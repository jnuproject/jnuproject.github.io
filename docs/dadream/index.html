01. 검토 목적 및 문서 성격

본 문서는 교내 주차 출차 혼잡 완화를 위한 모바일 기반 사전정산 서비스의 도입 가능성을 기술적으로 검토하기 위해 작성되었습니다. 현재 교내 주차장은 현장 키오스크(무인 정산기) 중심으로 운영되는 것으로 파악되며, 사용자가 출차 직전 현장에서 정산을 수행하는 구조상 특정 시간대에 정체가 발생할 가능성이 있습니다.

이에 따라 본 검토는 기존 주차관제 시스템을 전면 대체하는 것이 아니라, 기존 관제 시스템을 유지한 상태에서 모바일 앱을 통해 사전정산 기능을 확장할 수 있는지를 확인하는 데 목적이 있습니다.

문서 해석상 유의사항

본 문서는 시스템 구축 확정안이 아니라, 기술적 가능 방향과 선결 확인사항을 정리한 검토 문서입니다. 실제 구축 가능 여부는 기존 주차관제 시스템의 외부 연동 방식, 운영 정책, 업체 협조 범위, 보안 조건 등을 추가로 확인한 뒤 판단되어야 합니다.

02. 현재 파악된 시스템 환경 및 문제 정의

현재 운영 환경(파악 범위)

  • • 번호판 인식 기반 주차관제 시스템 운영
  • • 현장 무인 정산기(키오스크) 기반 사전정산 기능 존재 가능성
  • • 관리자용 Workstation 형태의 조회/통계 기능 존재 확인
  • • 차량 조회, 입출차 기록, 정산 관련 데이터가 관제 시스템 내부에 축적되는 구조로 추정

도입 필요성

  • • 출차 직전 현장 정산으로 인한 대기 가능성
  • • 키오스크 중심 정산 방식의 접근성 한계

03. 학생 개발팀 구현 현황 및 검토 범위

학생 개발팀은 현재 모바일 앱 프론트엔드 프로토타입을 구현한 상태이며, 사용자가 체감하는 핵심 흐름에 대한 UI/UX 검증을 우선 수행하였습니다. 다만 실제 서비스 구현은 관제 시스템과의 실연동이 전제되어야 하므로, 현재 단계는 클라이언트 프로토타입 구현 + 백엔드/연동 구조 초안 수립 단계로 보는 것이 적절합니다.

현재까지 준비된 범위

  • • 모바일 사전정산 UX 흐름 설계
  • • 차량 조회 화면 및 사용자 입력 흐름 구현
  • • 요금 표시 및 결제 진행 화면 프로토타입 구현
  • • 정산 완료 후 유효시간 표시 흐름 구현
  • • 서버 및 관제 연동을 고려한 구조 초안 마련

현재 미확정 범위

  • • 관제 시스템의 외부 조회 방식
  • • 정산 완료 상태의 외부 반영 방식
  • • 자동 출차 트리거 구조
  • • 운영 정책 세부 기준
  • • 업체 협조 범위 및 테스트 환경 제공 여부

프로토타입 화면 예시 (참고자료)

아래 화면은 실제 연동 완료 화면이 아니라, 사용자 흐름 검토를 위한 프로토타입 예시입니다. 향후 실제 데이터 연결 시 화면 구성 및 상태 표시는 운영 정책과 연동 방식에 따라 조정될 수 있습니다.

가. 차량 조회 입력 흐름

차량번호 일부 입력을 통해 사용자가 본인 차량 조회를 시도하는 흐름을 구현한 화면입니다.

나. 조회 결과 및 정산 대상 판별

등록 차량 예외 처리 또는 일반 정산 대상 차량 구분 등, 사용자 안내 흐름을 프로토타입 형태로 반영한 화면입니다.

다. 결제 진행 흐름

PG 연동을 가정한 결제 흐름 예시입니다. 실제 서비스에서는 서버 기준 승인 검증 절차가 병행되어야 합니다.

라. 정산 완료 후 유효시간 표시

사전정산 완료 후 유효시간을 사용자에게 안내하는 화면 예시입니다. 실제 유효시간 기준은 운영 정책 검토 후 확정되어야 합니다.

04. 기술 구조 검토: 모바일 사전정산 시스템의 기본 아키텍처

현재 검토하는 구조는 기존 관제 시스템을 유지하면서, 그 위에 모바일 사전정산 기능을 추가하는 형태입니다. 따라서 시스템은 크게 다음 네 계층으로 구분됩니다.

05. 결제 처리 구조 및 서버 기준 검증 필요성

모바일 앱 환경에서는 사용자 단말기에서 표시되는 금액이나 상태값을 그대로 신뢰할 수 없습니다. 따라서 결제의 최종 승인 및 상태 반영은 클라이언트가 아닌 서버 기준으로 처리되어야 합니다.

권장 결제 검증 흐름

  1. 사용자가 앱에서 결제를 시도함
  2. 앱은 결제 완료 신호 자체를 최종 결과로 확정하지 않고, 결제 관련 인증값만 서버로 전달함
  3. 사전정산 서버는 PG사와 Server-to-Server 방식으로 결제 승인 여부를 재검증함
  4. 서버가 승인된 결제 건에 한하여 내부 결제 상태를 갱신함
  5. 이후에만 관제 시스템 연동 절차를 진행함

금액 검증

서버가 본래 산출한 요금과 결제 승인 금액을 비교하여 금액 위변조 가능성을 낮출 필요가 있습니다.

상태 일관성

결제 성공과 관제 반영 성공은 분리하여 관리해야 하며, 중간 실패 상태를 별도로 추적할 필요가 있습니다.

중복 방지

주문번호 및 요청 식별자 기준으로 멱등성 처리를 적용하여 중복 결제 및 중복 반영을 방지해야 합니다.

위 구조는 일반적인 상용 결제 서비스 수준의 보안을 목표로 하는 설계 방향이며, 실제 적용 시에는 사용하는 PG사의 승인 절차와 학교 운영 기준에 따라 구체적인 구현 방식이 달라질 수 있습니다.

06. 관제 시스템 연동이 필요한 기술적 이유

모바일 사전정산 서비스가 실제로 동작하려면, 앱에서 결제가 이루어졌다는 사실만으로는 충분하지 않습니다. 최종적으로는 기존 주차관제 시스템이 해당 차량의 입차 정보, 정산 상태, 유효시간 등을 인지하고, 그 결과를 출차 제어에 반영할 수 있어야 합니다.

읽기(Read) 영역

  • • 차량번호 기준 입차 여부 확인
  • • 입차 시각 확인
  • • 등록 차량/정기권 여부 확인
  • • 필요 시 현재 주차 상태 확인

쓰기/반영(Control) 영역

  • • 정산 완료 상태 반영
  • • 정산 유효시간 반영
  • • 출차 시점의 상태 확인
  • • 내부 정책에 따른 차단기 제어 적용

기술적 핵심

조회 기능만으로는 모바일 사전정산 서비스가 완성되지 않으며, 정산 완료 상태를 기존 관제 시스템에 어떻게 반영할 수 있는지가 핵심 선결 과제입니다. 이 연동 방식은 API, 연계 서버, 내부망 인터페이스, 연계 DB 등 다양한 형태일 수 있으므로, 특정 방식 하나로 단정하기보다 현재 시스템 구조 확인이 우선되어야 합니다.

07. 학생 개발팀과 기존 업체 간 현실적인 역할 분담 방향

현재 단계에서 가장 현실적인 방향은 학생 개발팀이 모바일 앱, 사용자 경험, 결제 처리, 상태 관리 영역을 담당하고, 기존 관제 업체가 입차 원본 데이터, 등록 차량 판별, 차단기 제어, 내부 관제 로직을 유지하는 협력 구조입니다.

학생 개발팀 담당 가능 영역
  • • 모바일 앱 UI/UX 구현
  • • 사용자 차량 조회 요청 인터페이스
  • • 결제 요청 및 결제 상태 관리
  • • 사전정산 내역 저장
  • • 관제 연동을 위한 중계 서버 개발
기존 관제 시스템 유지 영역
  • • 번호판 인식 및 입출차 원본 데이터 관리
  • • 정기권/등록 차량 정책 관리
  • • 정산 상태 최종 반영 로직
  • • 차단기 및 현장 장비 제어
  • • 현장 운영 안정성 및 관제 책임

이러한 구조는 학생 개발팀이 기존 시스템 전체를 대체하는 것이 아니라, 기존 키오스크 중심 사전정산 기능을 모바일 채널로 확장하는 방향으로 해석할 수 있습니다. 이 경우 시스템 안정성과 사용자 편의성을 동시에 고려한 접근이 가능합니다.

08. 실제 구축 전 추가 확인이 필요한 사항

1. 외부 연동 방식 확인

기존 관제 시스템이 외부 시스템과 어떤 방식으로 연동 가능한지(API, 연계 서버, 내부망 인터페이스, 연계 DB 등) 확인이 필요합니다.

2. 정산 상태 반영 구조 확인

외부 결제 완료 정보를 관제 시스템이 수신·저장하고, 출차 판단에 활용할 수 있는 구조인지 확인이 필요합니다.

3. 테스트 환경 또는 샘플 데이터 제공 가능 여부

실제 개발 검증을 위해서는 최소한의 입차 데이터 예시, 등록 차량 여부 예시, 응답 포맷 예시 또는 테스트 환경이 필요합니다.

4. 운영 정책 관련 추가 검토 필요 사항

  • • 사전정산 이후 유효시간 초과 시 추가요금 처리 방식
  • • 앱 선결제 금액과 현장 정산 간 차감/정산 처리 방식
  • • 공휴일 기준, 야간 기준, 익일 초기화 기준
  • • 차량번호 일부 입력(예: 4자리) 조회 시 중복 차량 처리 방식
  • • 정기권 차량 및 예외 차량 정책 처리 기준

09. 행정 부서 및 관제 업체 협의 요청사항

학생 개발팀이 모바일 앱 및 서버 영역을 구체화하기 위해서는, 학교 주관 부서와 기존 관제 업체 간의 기술 협의가 선행될 필요가 있습니다. 특히 다음 항목에 대한 확인이 요청됩니다.

요청사항 A

입차 정보 및 차량 권한 조회 가능 여부

특정 차량의 입차 시각, 현재 주차 여부, 등록 차량 여부 등을 외부 시스템이 조회할 수 있는 연동 방식 제공 가능 여부를 확인할 필요가 있습니다.

요청사항 B

정산 완료 상태 반영 가능 여부

앱 결제 완료 후 해당 상태를 기존 관제 시스템에 반영하고, 출차 판단에 활용할 수 있는 구조가 존재하는지 확인이 필요합니다.

요청사항 C

기술 협의 및 테스트 절차 마련

필요 시 총무·시설 담당 부서, 관제 업체, 학생 개발팀, 관련 전문가가 함께 참여하는 기술 협의 자리를 통해 연동 범위와 테스트 절차를 정리할 필요가 있습니다.

10. 종합 결론
